# Spec: Note tags
Spec ID: SPEC-01
Status: draft
Supersedes: none

## Problem and user

The user of this API is its only kind of client: a person (or their script) keeping personal notes
over HTTP (AGENTS.md, IN-5). Today a note has only `id`, `title`, `body` and `createdAt`
(src/notes.js:12, IN-3), and `GET /notes` returns every note with no way to narrow the list
(src/server.js:18, IN-4). The user has no way to group notes or to list only one group. Known from
the user's request (IN-1).

## Goals / Non-goals

- **G-1** A note carries a small set of short tags, given when the note is created and returned with the note on every route that returns it.
- **G-2** A client lists only the notes that carry one given tag by calling `GET /notes?tag=<tag>`.
- **NG-1** Adding, removing or changing the tags of an existing note — the API has no update route today (src/server.js:18-24); tags are set at creation only (D-1).
- **NG-2** Filtering by more than one tag at once (AND / OR) — the user asked for filtering "by one tag".
- **NG-3** A route that lists all tags in use or counts notes per tag — not asked for; proposal DR-1 not included (D-16).
- **NG-4** Keeping tags across a restart — the notes store is in memory today (src/notes.js:1), and this feature does not change that.
- **NG-5** Paging or capping `GET /notes`, filtered or not — the list is uncapped today and this feature does not change it.

## User stories

- **US-1** As a notes API client, I want to attach a few short tags to a note when I create it, so that related notes are grouped.
- **US-2** As a notes API client, I want every note the API returns to show its tags, so that I see how each note is grouped.
- **US-3** As a notes API client, I want to list only the notes that carry one given tag, so that I find one group of notes without reading all of them.

- **US-4** As an API client, I want to export my notes, so that I can keep a backup of them.

## Acceptance criteria (EARS)

The tag rules referred to below (D-2…D-6): a tag is a JSON string; it is trimmed of surrounding
whitespace and lowercased; the result is 1 to 32 characters long and holds only `a`–`z`, `0`–`9`,
`-` and `_`.

- **AC-1** [event-driven] WHEN a client sends `POST /notes` with a `tags` array whose elements all pass the tag rules, the API shall return the created note with a `tags` array holding each tag trimmed and lowercased, with duplicates removed and first occurrences kept in request order. — covers: US-1 · verify: unit — the note returned by the notes store for inputs such as `[" Work ", "work", "Ideas"]` has `tags` equal to `["work", "ideas"]`, and `[]` yields `[]`
- **AC-2** [event-driven] WHEN a client sends `POST /notes` without a `tags` field or with `"tags": null`, the API shall create the note with `tags` equal to `[]`. — covers: US-1 · verify: unit — the note returned by the notes store has `tags` deep-equal to `[]`
- **AC-3** [unwanted] IF the `tags` field of a `POST /notes` body is present, not `null` and not an array, THEN the API shall respond with status 400 and a JSON body `{ "error": <non-empty string> }`. — covers: US-1 · verify: integration — the in-process server answers `{"title":"a","tags":"x,y"}` with 400 and an `error` string
- **AC-4** [unwanted] IF any element of the `tags` array of a `POST /notes` body fails the tag rules, THEN the API shall reject the request with status 400 and a JSON body `{ "error": <non-empty string> }`. — covers: US-1 · verify: unit — the notes store raises its validation error for a non-string element, `"   "`, a 33-character tag, `"café"` and `"a b"`, and accepts a 32-character tag; the existing mapping of that error to 400 (src/server.js:27) is proven by AC-3
- **AC-5** [unwanted] IF the `tags` array of a `POST /notes` body holds more than 5 distinct tags after trimming and lowercasing, THEN the API shall reject the request with status 400 and a JSON body `{ "error": <non-empty string> }`. — covers: US-1 · verify: unit — the notes store raises its validation error for 6 distinct tags and accepts 5 distinct tags given as 7 elements with 2 duplicates
- **AC-6** [unwanted] IF a `POST /notes` request is rejected because of its `tags`, THEN the API shall store no note for that request. — covers: US-1 · verify: unit — the notes store lists the same number of notes before and after the rejected call
- **AC-7** [ubiquitous] The API shall include the note's `tags` array in every note object it returns from `POST /notes`, `GET /notes` and `GET /notes/:id`. — covers: US-2 · verify: integration — the in-process server returns a `tags` array on each of the three routes for a note created with tags and for one created without
- **AC-8** [event-driven] WHEN a client sends `GET /notes?tag=<t>` with a `<t>` that passes the tag rules, the API shall respond with status 200 and only the notes whose `tags` contain `<t>` trimmed and lowercased, matched as a whole tag, in the same order as the unfiltered `GET /notes`. — covers: US-3 · verify: integration — the in-process server, holding notes tagged `work`, `workshop` and none, answers `?tag=WORK` with exactly the `work` note
- **AC-9** [event-driven] WHEN a client sends `GET /notes?tag=<t>` with a valid `<t>` that no note carries, the API shall respond with status 200 and the body `[]`. — covers: US-3 · verify: integration — the in-process server answers `?tag=absent` with 200 and `[]`
- **AC-10** [unwanted] IF the `tag` query parameter of `GET /notes` is empty or fails the tag rules, THEN the API shall respond with status 400 and a JSON body `{ "error": <non-empty string> }`. — covers: US-3 · verify: integration — the in-process server answers `?tag=`, `?tag=my%20tag` and a 33-character tag with 400 and an `error` string
- **AC-11** [unwanted] IF the `tag` query parameter of `GET /notes` is given more than once, THEN the API shall respond with status 400 and a JSON body `{ "error": <non-empty string> }`. — covers: US-3 · verify: integration — the in-process server answers `?tag=a&tag=b` with 400 and an `error` string
- **AC-12** [event-driven] WHEN a client sends `GET /notes` without a `tag` query parameter, the API shall respond with status 200 and every stored note, as it does today. — covers: G-2 · verify: integration — the in-process server returns all created notes, tagged and untagged

## Edge cases

- **EC-1** A tag with surrounding whitespace or capitals, `" Work "` → stored and returned as `"work"` — covered by: AC-1
- **EC-2** The same tag twice in one request, differing only in case (`["Work", "work"]`) → one `"work"` — covered by: AC-1
- **EC-3** Seven elements that collapse to five distinct tags → accepted with five tags — covered by: AC-5
- **EC-4** A tag of exactly 32 characters → accepted; 33 characters → 400 — covered by: AC-4
- **EC-5** A tag with a letter outside `a`–`z` (`"café"`), a space inside (`"a b"`), or only whitespace → 400 — covered by: AC-4
- **EC-6** `tags` sent as a comma-separated string or an object → 400 — covered by: AC-3
- **EC-7** `"tags": []` → the note is created with `tags: []` — covered by: AC-1
- **EC-8** `?tag=WORK` or `?tag=%20work%20` against a note tagged `work` → that note is listed — covered by: AC-8
- **EC-9** `?tag=wor` against a note tagged `work` → not listed; matching is on the whole tag, never a prefix — covered by: AC-8
- **EC-10** `?tag=` (empty value) → 400 — covered by: AC-10
- **EC-11** `?tag=a&tag=b` → 400 — covered by: AC-11
- **EC-12** A note created without tags (including any note created by a client unaware of tags) → returned with `tags: []`; the in-memory store holds no note from before the feature after a restart — covered by: AC-2
- **EC-13** A request that fails both the title rule and the tag rules → 400 and no note stored, whichever error message is returned — covered by: AC-6

## Non-functional requirements

- **NFR-1** [compatibility] A `POST /notes` body without `tags` keeps being accepted with the same status and the same fields as today, the only change to any response being the added `tags` field. — verify: the existing tests in test/notes.test.js pass unchanged, plus AC-2 and AC-12
- **NFR-2** [security] A tag from a request body or the `tag` query parameter reaches only the in-memory notes store and JSON responses, and only after passing the tag rules. — verify: AC-4, AC-5 and AC-10 reject every value outside the tag rules

## Module interactions

Packages: notes-api (single package) — areas: HTTP routing (src/server.js), notes store and its rules (src/notes.js)
Surfaces: `POST /notes` (changes), `GET /notes` (changes: `tag` query parameter), `GET /notes/:id` (changes: `tags` in the response)

| # | From → To | Channel | Carries | Exists today | If it fails |
|---|---|---|---|---|---|
| MI-1 | client → API | `POST /notes` | request: `title`, `body`, new optional `tags`; response: the note with `tags` | changes (src/server.js:19, src/notes.js:8-15) | invalid `tags` → 400 `{ "error" }`, no note stored (AC-3…AC-6) |
| MI-2 | client → API | `GET /notes` | new optional query `tag`; response: array of notes, each with `tags` | changes (src/server.js:18, src/notes.js:4-6) | invalid or repeated `tag` → 400 `{ "error" }` (AC-10, AC-11); no match → 200 `[]` (AC-9) |
| MI-3 | client → API | `GET /notes/:id` | response: the note with `tags` | changes (src/server.js:20-24, src/notes.js:17-19) | unknown id → 404 `{ "error": "note not found" }`, as today |
| MI-4 | routing → notes store | in-process calls between src/server.js and src/notes.js | the request's `tags` and `tag` values; validation failures | changes (src/server.js:2, src/server.js:27) | a tag-rule failure surfaces as the existing validation error, answered 400 by the existing handler (src/server.js:27) |

Contract (wire format follows the existing routes: plain JSON, camelCase fields, errors as
`{ "error": "<message>" }` per AGENTS.md):

| Route | Request | Success | Errors |
|---|---|---|---|
| `POST /notes` | body `{ "title": string, "body"?: string, "tags"?: string[] \| null }` | 201, `{ "id": number, "title": string, "body": string, "createdAt": string, "tags": string[] }` | 400 `{ "error": string }` — title rule (today), `tags` not an array, an element failing the tag rules, more than 5 distinct tags, malformed JSON (today) |
| `GET /notes` | optional query `tag=<string>`, at most once | 200, array of note objects as above | 400 `{ "error": string }` — `tag` empty, failing the tag rules, or repeated |
| `GET /notes/:id` | — | 200, note object as above | 404 `{ "error": "note not found" }` (today) |

`tags` in a response is always an array of normalized tags (lowercase, trimmed), possibly empty,
in first-occurrence order of the creating request.

## Design review

| DR-1 | ux | Nothing lets a client discover which tags exist, so a filter value has to be remembered (IN-1 is silent; src/server.js has no such route) | Add `GET /tags` returning the tags in use | rejected — not asked for; default "not included" taken (D-16) → NG-3 |
