# Spec: Tags on notes
Spec ID: SPEC-01
Status: approved
Supersedes: none

## Problem and user

The user of notes-api is a client of the HTTP API that keeps personal notes (AGENTS.md). Today a
note carries only `id`, `title`, `body` and `createdAt` (src/notes.js:12), and `GET /notes` returns
every note with no way to narrow the list (src/server.js:18). A client that wants to group notes
has nowhere to record the group and no way to ask for one group. The need is stated in the task
text (IN-1): a note carries a few short tags, and `GET /notes` is filtered by one tag.

## Goals / Non-goals

- **G-1** A client attaches up to 10 short tags to a note when it creates it, and sees those tags on every note the API returns.
- **G-2** A client lists only the notes that carry one given tag with `GET /notes?tag=<tag>`.
- **NG-1** Adding, changing or removing the tags of an existing note — the API has no update route today (src/server.js:18-24); tags are set when the note is created.
- **NG-2** Filtering by more than one tag, or by a prefix or substring of a tag — the task asks for a filter by one tag.
- **NG-3** An endpoint that lists every tag in use — not asked for (DR-2).
- **NG-4** Persisting tags across restarts — the store is in memory (src/notes.js:1), and stays so.
- **NG-5** Paging or capping `GET /notes` — the feature leaves the list size as it is today.

## User stories

- **US-1** As a notes API client, I want to send tags with a new note, so that I group my notes.
- **US-2** As a notes API client, I want every note I read to show its tags, so that I see which group it belongs to.
- **US-3** As a notes API client, I want to list the notes that carry one tag, so that I find a group without reading every note.

## Acceptance criteria (EARS)

- **AC-1** [event-driven] WHEN a client sends `POST /notes` with a `tags` array of valid tags, the API shall return the created note with `tags` holding each tag trimmed and lowercased, in the order sent. — covers: US-1 · verify: unit — the note returned by the create operation for `["  Work ", "home"]` has `tags` equal to `["work", "home"]`
- **AC-2** [event-driven] WHEN a client sends `POST /notes` without a `tags` field, the API shall create the note with `tags` equal to `[]`. — covers: US-1 · verify: unit — the returned note has `tags: []`
- **AC-3** [event-driven] WHEN the `tags` of a `POST /notes` request hold the same tag more than once after trimming and lowercasing, the API shall keep only the first occurrence of that tag. — covers: US-1 · verify: unit — `["a", " A ", "b", "a"]` is stored as `["a", "b"]`
- **AC-4** [unwanted] IF the `tags` field of a `POST /notes` request is present and is not an array whose elements are all strings, THEN the API shall respond `400` with `{"error": "tags must be an array of strings"}`. — covers: US-1 · verify: integration — status and body for `tags: "work"`, `tags: null` and `tags: [1]` against the app in-process
- **AC-5** [unwanted] IF a tag of a `POST /notes` request, after trimming and lowercasing, is empty, is longer than 32 characters, or holds a character other than `a`–`z`, `0`–`9`, `-` and `_`, THEN the API shall respond `400` with `{"error": "tag is invalid"}`. — covers: US-1 · verify: integration — status and body for `""`, `"   "`, a 33-character tag, `"my tag"` and `"café"`; a 32-character tag is accepted
- **AC-6** [unwanted] IF the `tags` of a `POST /notes` request hold more than 10 distinct tags after trimming, lowercasing and removing duplicates, THEN the API shall respond `400` with `{"error": "too many tags"}`. — covers: US-1 · verify: integration — 11 distinct tags are refused; 10 distinct tags, and 12 tags of which 10 are distinct, are accepted
- **AC-7** [unwanted] IF a `POST /notes` request is refused for its tags, THEN the API shall store no note. — covers: US-1 · verify: unit — the list of notes has the same length before and after the refused create
- **AC-8** [ubiquitous] The API shall include a `tags` array in every note it returns from `POST /notes`, `GET /notes` and `GET /notes/:id`. — covers: US-2 · verify: integration — the `tags` field is present on the response of each of the three routes against the app in-process
- **AC-9** [event-driven] WHEN a client sends `GET /notes?tag=<tag>`, the API shall respond `200` with exactly the notes whose `tags` contain that tag after it is trimmed and lowercased, in the order unfiltered `GET /notes` returns them. — covers: US-3 · verify: integration — with notes tagged `work`, `work-log` and none, `?tag=WORK` returns only the `work` note
- **AC-10** [event-driven] WHEN a client sends `GET /notes?tag=<tag>` with a valid tag that no note carries, the API shall respond `200` with `[]`. — covers: US-3 · verify: integration — status and body for an unused tag
- **AC-11** [unwanted] IF the `tag` query parameter of `GET /notes` is empty or is not a valid tag by the rule of AC-5, THEN the API shall respond `400` with `{"error": "tag is invalid"}`. — covers: US-3 · verify: integration — status and body for `?tag=` and `?tag=my%20tag`
- **AC-12** [unwanted] IF the `tag` query parameter appears more than once in a `GET /notes` request, THEN the API shall respond `400` with `{"error": "only one tag filter is allowed"}`. — covers: US-3 · verify: integration — status and body for `?tag=a&tag=b`
- **AC-13** [event-driven] WHEN a client sends `GET /notes` without a `tag` query parameter, the API shall respond `200` with every note, in the order it returns them today. — covers: US-3 · verify: integration — tagged and untagged notes are all returned

## Edge cases

- **EC-1** `tags` is `[]` → the note is created with `tags: []` — covered by: AC-1
- **EC-2** `tags` is `null`, a string, or holds a number → refused with `400` — covered by: AC-4
- **EC-3** `" Work "` and `"work"` in the same request → one tag `work` is stored — covered by: AC-3
- **EC-4** 10 distinct tags, or 12 tags of which 10 are distinct → accepted; 11 distinct tags → refused with `400` — covered by: AC-6
- **EC-5** a tag of exactly 32 characters → accepted; a tag of 33 characters → refused with `400` — covered by: AC-5
- **EC-6** a tag with a letter outside `a`–`z` (`café`) or an inner space (`my tag`) → refused — covered by: AC-5
- **EC-7** `?tag=work` and a note tagged `work-log` → that note is not returned; the match is the whole tag — covered by: AC-9
- **EC-8** `?tag=WORK` or `?tag=%20work%20` → matches notes tagged `work` — covered by: AC-9
- **EC-9** `?tag=` → refused with `400` — covered by: AC-11
- **EC-10** `?tag=a&tag=b` → refused with `400` — covered by: AC-12
- **EC-11** other query parameters beside `tag` → ignored, as `GET /notes` ignores the query today (src/server.js:16-18) — covered by: AC-9
- **EC-12** a `POST /notes` refused for its tags → no note is left behind in `GET /notes` — covered by: AC-7
- **EC-13** notes that existed before the feature → none survive a restart, since the store is in memory (src/notes.js:1); every note the running API returns carries `tags` — covered by: AC-8

## Non-functional requirements

- **NFR-1** [security] A note stores at most 10 tags of at most 32 characters each, drawn from `a`–`z`, `0`–`9`, `-` and `_`; nothing outside that rule reaches the store. — verify: the tests of AC-4, AC-5 and AC-6
- **NFR-2** [compatibility] The fields `id`, `title`, `body` and `createdAt` keep their names and types, and a `POST /notes` request without `tags` is accepted as today. — verify: integration — an existing-shape request and response compared field by field
- **NFR-3** [compatibility] Every error the feature adds is a JSON body `{ "error": "<message>" }` with a 4xx status, as AGENTS.md requires. — verify: the tests of AC-4, AC-5, AC-6, AC-11 and AC-12

## Module interactions

Packages: notes-api (single package: routing in `src/server.js`, the notes store and its rules in `src/notes.js`)
Surfaces: `POST /notes` (accepts `tags`), `GET /notes` (accepts `tag`), `GET /notes/:id` (returns `tags`)

| # | From → To | Channel | Carries | Exists today | If it fails |
|---|---|---|---|---|---|
| MI-1 | client → API | POST /notes | request `title`, `body`, `tags`; response the note with `tags` | changes (src/server.js:19, src/notes.js:8-15) | `400` with an error body (AC-4, AC-5, AC-6); no note stored (AC-7) |
| MI-2 | client → API | GET /notes | query `tag`; response the notes, each with `tags` | changes (src/server.js:18, src/notes.js:4-6) | `400` with an error body (AC-11, AC-12) |
| MI-3 | client → API | GET /notes/:id | response the note with `tags` | changes (src/server.js:20-24, src/notes.js:17-19) | `404 {"error": "note not found"}`, as today |

Contract (wire format follows the existing routes: JSON body, camelCase fields, errors as `{ "error": "<message>" }`):

- Note object: `id` number · `title` string · `body` string · `createdAt` string (ISO 8601) · `tags` string[] (new; 0–10 items, each 1–32 characters of `a`–`z`, `0`–`9`, `-`, `_`; no duplicates; order of first occurrence in the request).
- `POST /notes` body: `title` string, required (as today) · `body` string, optional (as today) · `tags` string[], optional (new). Response `201` with the note.
- `GET /notes` query: `tag` string, optional, at most once (new). Response `200` with an array of notes.
- New errors, all `400`: `tags must be an array of strings` · `tag is invalid` · `too many tags` · `only one tag filter is allowed`.

## Design review

Sources reviewed: IN-1, IN-3, IN-4. No design source was supplied; the feature has no screen, so the states, layout, accessibility and copy rows of a screen review do not apply.

| # | Kind | Finding | Proposal | Decision |
|---|---|---|---|---|
| DR-1 | missing state | IN-1 gives no way to change tags after creation, and src/server.js:18-24 has no update route | Add a route that changes the tags of an existing note | rejected — not asked for; tags stay creation-only (NG-1) |
| DR-2 | ux | A client grouping notes has no way to discover which tags it already used | Add `GET /tags` listing tags in use | rejected — not asked for; adds a route (NG-3) |
| DR-3 | corner case | IN-1 does not say whether `Work` and `work` are one tag | Trim and lowercase tags on write and on filter | accepted → AC-1, AC-9 |
| DR-4 | corner case | IN-1 says "a few short tags" with no number | At most 10 tags of at most 32 characters, from `a`–`z`, `0`–`9`, `-`, `_` | accepted → AC-5, AC-6 |
| DR-5 | corner case | IN-1 does not say what a filter on an unused tag returns | `200` with `[]`, not `404` | accepted → AC-10 |
| DR-6 | corner case | IN-1 says "one tag"; a request may repeat `tag` | Refuse a repeated `tag` with `400` instead of silently picking one | accepted → AC-12 |
| DR-7 | corner case | IN-1 does not say what happens to duplicate tags in one request | Keep the first occurrence; refuse nothing | accepted → AC-3 |
